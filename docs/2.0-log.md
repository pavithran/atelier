## Task 1: the server runs under Node with SQLite Ledgers (t396)

Built by claude-code/opus-5.5 on 2026-10-28, branch `2.0/t1-node-runtime`.

**What.** `cli/serve.mjs` runs one process per environment and serves `src/index.ts`'s `fetch` over Node's `http` (`src/runtime/server.mjs`). Module hooks load the Workers sources unchanged (`src/runtime/loader.mjs`). Each Ledger Durable Object is a SQLite file of its own under `DATA/ledgers` (`node:sqlite`, mode 600), with:
- a queue per object, so calls never interleave;
- one transaction per call;
- savepoints for `transactionSync`;
- structured clones across the stub;
- errors crossing as plain Errors;
- alarms kept in the object's own file and delivered at least once (`src/runtime/namespace.mjs`).

Artifacts, R2 and the landing Workflow refuse with `not_supported` until later tasks. The 132 Workers test files are skipped by name (`test/workers-skipped.txt`); `ATELIER_WORKERS_TESTS=1` still runs them in workerd.

**Decisions taken while building.**
- **One SQLite file per Durable Object name**, not one file per environment as the design said. The Ledger's SQL, dump and import stay unchanged, and no table names need prefixing.
- **`node:sqlite`** (built into Node 26) instead of `better-sqlite3`: no native build.
- **Every call commits, thrown or not**, as the Workers runtime keeps writes made before a throw outside `transactionSync`.

**Criteria.**
1. `serve` answers `/api/version`, and `atelier login`, `new`, `ls`, `show`, `edit` and `decide` work against it: `test/node-server.test.mjs`, first test.
2. Node test files pass, with `src/rules.ts` and `test/rules.test.ts` unchanged and the Workers tests skipped by name. Full run on the merged head 527d864a (both pieces): 4,505 pass, 0 fail, 3 skipped as before, and 132 Workers files skipped by name; typecheck clean.
3. Calls to one Ledger never interleave, and concurrent creates on the real Ledger stay ordered. An alarm fires within a second, the real Ledger's included, after a restart too: `test/node-server.test.mjs`.
4. The data directory is mode 700 and every file in it 600. No file holds the owner token, the override secret or a minted agent token: `test/node-server.test.mjs`.

**Review.** codex/gpt-6-astra, four rounds.
- **Round 1, reject.**
  1. *A BigInt fallback re-ran writes:* fixed; every statement reads BigInts.
  2. *An alarm was deleted before its handler committed:* fixed.
  3. *`scheduled()` is not on timers:* refuted, because the plan gives it to task 8; astra accepted that in round 2.
  4. *Arguments were cloned late:* fixed.
  5. *Tests:* added for the real Ledger's alarm, retries and savepoints.
- **Round 2, reject.** A replacement alarm for the same moment was lost, and alarm changes escaped the handler's transaction. Fixed by moving each alarm into the object's own file (`_atelier_alarm`, which the dump skips), with a generation, written in the call's transaction. Tests added for each case.
- **Round 3, reject.** Rolling back a savepoint restored the alarm row but not its timer. Fixed: the timer is set again from the row after every call settles and after every rollback. Test added.
- **Round 4, approve** (about 12:25 pm), no findings.

## Task 2: plain Git repositories with a hook that enforces the task branch (t397)

Built by claude-code/opus-5.5 on 2026-10-28, branch `2.0/t2-git-hook`.

**What.** One bare repository per project, served over HTTP through `git http-backend` (`src/git/`).
- **Grants.** Credentials are grants kept by SHA-256. A task grant counts only while the task's Ledger records it as the item's write token (`git:HASH`), so the Ledger's own changes of holder revoke it. `POST /api/projects/P/git-token` mints read and task grants.
- **The hook.** `hooks/pre-receive` applies rules 1 to 4 of design section 4.4.
- **Docs.** `docs/branches.md` states the mechanism and the macOS user boundary it rests on.

**Criteria.** 1 to 4: `test/git-hook.test.mjs`, which pushes with the real client against the real hook. 5: `docs/branches.md`.

**Review.** opencode/glm-5.3 approved, finding no way for a credential to write a ref it should not; it ran the tests (5/5). Its five follow-ups were all fixed before the merge:
1. Expired and revoked grants are now pruned daily.
2. A Git URL resolves a project by any name it has had, as every other route does.
3. A malformed name is answered 404 instead of 500.
4. A client gone mid-request kills its backend.
5. A repository is set up once per process, not on every request.

A test covers the malformed name and the rename. Fixing these turned up a hang in the server's `close()` on kept-alive connections; it now closes them once requests in flight finish.

## Task 3: the secret scan and the private-file guard run in the hook (t398)

Built by claude-code/opus-5.5 on 2026-10-28, with its follow-ups by claude-code/sonnet-5.5; branch `2.0/t3-hook-scans`.

**What.** `hooks/pre-receive` runs rules 5 and 6 after rules 1 to 4 (`src/git/scan.mjs`), reusing `scanHistory` and `readAllowanceList` from `src/secret-scan.ts` and `privateCommits` from `cli/private-guard.mjs`.
- **What is scanned:** on a task, plan or dev branch, everything the head has that the project's branch lacks, by full ancestry, capped at 1,000 commits and failing closed past the cap.
- **What refuses:** a key-shaped line the owner has not cleared refuses the push, naming file and line, never the value. An unscanned file is recorded and blocks at the gate on a task. On a push with no task (owner, landing, dev), it refuses.
- **Passing data to the hook:** the server gives the hook a per-request policy file (clearances and private paths, mode 600) and reads back its report, which becomes the item's scan record, kept per head.

**Criteria.**
1. A refused push names the finding; a cleared or allowed line passes.
2. The scan record is on the item.
3. No value reaches disk, the environment or a log.

All three are shown in `test/git-scan.test.mjs` and `test/git-hook.test.mjs`, which use the real hook and the real git client. The audit's amendments are tested too: a file over 8 MiB, and a merge carrying an allowed line.

**Review.** opencode/glm-5.3.
- **Round 1, approve,** with seven follow-ups: unscanned files on pushes with no item, the report slot keyed by head, a commit cap, sweeping leftovers, missing tests, and notes for the landing-grant task. The first five were fixed; the last two became notes in `docs/branches.md`.
- **Round 2, approve.** Its one low finding, a scan row left by a push that ends after its task closed, was fixed before the merge.

### G10, retries in the CLI

Built by claude-code/sonnet-5.5, with fixes by claude-code/opus-5.5; branch `2.0/g10-retry`.
- **What.** `request()` retries three times (1, 2 and 4 seconds) only:
  - reads;
  - pushes, idempotent by head;
  - writes that provably never left: connection refused, DNS or no route on the original URL, with redirects not followed on writes.

  Any other uncertain write stops with "may have applied: run ...". That doubt survives later refusals.
- **Commands safe to rerun by hand.** submit, review-withdraw, undispatch, abandon, release and approve answer "already" and exit 0. Each "already" is bound to what the command named and given only after the request's own validation; a release records who released (`by`).
- **Review.** codex/gpt-6-astra, four rounds.
  - Round 1 rejected the first design, a server-side cache of idempotency keys: it stored plaintext credentials and could not prove exactly-once. That design was removed.
  - Round 2 rejected automatic retries of writes, which were not bound to their target. The retries were narrowed to the three cases above.
  - Round 3 found doubt lost on two exits, and a repeated release that skipped its note check. Both fixed.
  - Round 4, approve.

### G8, every refusal names the next command

Built by claude-code/sonnet-5.5, branch `2.0/g8-next-command`.

**What.** `RuleError` carries an optional `next`, the exact command that resolves it, or "only the developer can: ...". It crosses the Ledger stub appended to the message, and `parseRuleError` reads it; older messages still parse. The error body is `{error, detail, next}`. The CLI prints `next:` on its own line, and under `--json` or `ATELIER_JSON=1` it prints `{code, detail, next}` on stderr.

**Counts.** Of 308 codes, 176 carry a `next` and 132 are exempt, each as input validation or a guarded route, which the test enforces. The 79 claim, push, submit, land and record-merge codes carry `next` at every raise site.

**Tests.** `test/refusal-next.test.mjs` scans every `new RuleError(` and fails on a computed code that is not listed. `test/refusal-next.server.test.mjs` drives refusals through the Node server and the CLI, as text and as JSON.

**Review.** opencode/glm-5.3 approved it, and its follow-ups were fixed before the merge:
- a scanner blind to computed codes;
- `no_item` and `token_revoked` naming no command;
- `no_criteria` offering an owner-only command to anyone;
- `main_moved` pointing to a step that loops;
- the counts.

**Found after G10 merged.** G10's builder had not run every test that drove a 5xx. The full suite at `af367557` found eleven tests across six files. In fixing them, two real G10 defects came to light. The last retry's message dropped the server's words. Check-result posts, which `postEvidence` had retried before G10, no longer retried; they are now recorded once per identical result and are on the list of writes safe to repeat.

### G5, the runner keeps every finished piece of work and remembers nothing the server lacks

Built by claude-code/sonnet-5.5 (rounds 1 to 3) and claude-code/opus-5.5 (rounds 4 and 5, after three rejections, under PAVI's standing rule); branch `2.0/g5-runner-keeps`.

**What.**
- **Unfinished work:** a harness that ends with changes and no commit gets a `wip` commit, pushed through the guarded push, and a release note naming it. A refused push says why.
- **One claim per dispatch:** a second runner gets 409 `claimed`, naming the holder; the dispatch is reassignable once the holder's runner falls silent.
- **Blocks:** a block is the server's record alone. A local marker never decides, and an unblock is read from the server's times.
- **Memory on the server:** the runner's skips, waits and provider pauses go with each poll, the server keeps them and gives them back after a restart. `atelier forget-skip tN` clears a remembered skip.
- **Same-exit counts:** for builds, reviews, criteria reviews and pre-reviews, the count is the server's, keyed by job, task and head. It resets on a new head, a different or unsigned exit, or a valid verdict. A task that closes ends its open review claims.

**Review.** codex/gpt-6-astra, five rounds.
1. Reject: counts kept per runner, local waits and pauses, sandbox text read as a block, a marker that decided, signatures truncated, and no clear command.
2. Reject: criteria-review and pre-review counts still local, and an unblock that depended on the marker.
3. Reject: counts keyed by a request id that changes, unapplied releases counted, and the runner's local map still deciding.
4. Reject: a valid verdict did not clear the streak, and a failure after abandon recreated a count.
5. Approve.

**Merge.** G5 conflicted with G8 in two refusals; both changes were kept. G5's branch had committed its `node_modules` symlink, and checking it out removed this worktree's ignored `node_modules` folder. The dependencies were reinstalled with `npm ci`, and `.gitignore` now ignores a `node_modules` link as well as a folder. After the merge, G8's audit caught a new code with no `next` (`claimed`), and a Workers spec still expected G5's old 403; both were fixed.

**Full suite** on the merged head `9b4ae015`: 4,605 pass, 3 fail. The three were the ones fixed just above, at `4ba78d3f`.

### G16, record-merge applies the gate's independence

Built by claude-code/opus-5.5, branch `2.0/g16-record-merge`.

**What.** `recordedMergeIndependence` in `src/rules.ts`, called from `recordMergeAllowed`, counts the named approvals with the gate's own helpers (`countingReviews`, `approvalsCounted`, `independentApproval`). It classifies the change from the paths observed at the merged commit; unobserved paths count as protected. A named approval takes its proof from the Ledger. An unproved one is refused under `noOverride`; otherwise it counts only as an override, and the record names it. Fast mode keeps the gate's own rule. The `harnessEligible` guard was already gone (2026-10-25); `MergeContext.contributors`, which only fed it, is removed.

**Consequence.** A valid record-merge now needs the reviewer's own review in the Ledger, or a developer-recorded verdict answering a request that reviewer claimed, exactly as the gate accepts.

**Review.** codex/gpt-6-astra, three rounds.
1. Reject: a withdrawn approval came back, and an approval without proof passed. Both were reproduced and fixed, with regression tests.
2. Reject: tier approvals were not normalized when several reviews are needed. Fixed by reusing `approvalsCounted`.
3. Approve, after 64 in-memory parity checks between the gate and record-merge.
